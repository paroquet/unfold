## 1. 产品愿景

**让人能够理解、验证并承担每一次软件变更的决策，而不被代码的生成速度和呈现方式淹没。**

Unfold 将代码变化展开为有顺序、有上下文、有证据的评审过程：先理解意图与行为，再检查契约、执行路径和风险，最后回到真实代码与测试作出判断。

交接文件提出一个值得验证的产品假设：AI 降低代码生产成本之后，人类重建上下文与验证正确性的成本，会成为更突出的约束。Unfold 围绕这个假设设计产品，并通过真实评审实验验证价值，不把行业预测当成已证实事实。

产品定位是 **AI 辅助的代码理解与人类验证工具**。AI 承担变化组织、上下文检索和解释；人决定意图是否合理、实现是否正确、架构是否可接受、风险是否可以承担。

Tagline：**Unfold your change before you review it.**

## 2. 用户与第一切入口

第一用户是每天使用多 worktree、多 coding agent 的技术负责人或资深开发者。他面对的典型场景是：agent 完成一轮开发，工作区里既有已有文件的修改，也有尚未提交的新文件；他需要理解改动、给出意见，再检查修复。

这一场景的主要成本包括：

- 从文件列表重建“这个功能到底改变了什么”。
- 在接口、实现、调用方与测试之间反复跳转。
- 区分真正的行为变化与格式调整、机械迁移。
- 判断 agent 第二轮修改是否解决了意见、是否引入新问题。
- 在被打断后找回自己看过的版本、未解决的问题与阅读位置。

v1 聚焦现有 spec 确定的闭环：**本地快照 → 按章阅读与导航 → 结构化批注 → 回传同一个 agent → 增量重看**。GitHub PR、多人与跨仓库协作属于后续方向。

## 3. 核心价值：从“看过”走向“验证了什么”

产品应帮助 reviewer 回答五个问题：

1. **为什么改？** 原始任务、作者说明与代码变化是否一致？
2. **改变了什么？** 用户行为、接口契约、状态与副作用有哪些差异？
3. **影响在哪里？** 哪些入口、调用方、错误路径或生命周期受到影响？
4. **凭什么相信？** 哪段代码、哪个测试或运行结果支持解释？还有什么未知？
5. **我验证到哪里了？** 检查了哪个版本、哪些问题未解决、更新后哪些判断需要重看？

一次点击或一次文件打开只代表阅读动作，不能自动代表正确性已经验证。产品应明确区分阅读记录、证据检查与人类判断。

## 4. 与软件工程最佳实践的结合

以下产品设计是对工程实践的应用与延伸，不意味着相关资料已经证明 Unfold 的效果。

| 工程实践 | 产品中的具体落点 | 需要守住的边界 |
|---|---|---|
| 小而聚焦的变更 | 按行为与依赖组织章节，把契约、实现、调用方和对应测试放在可连续阅读的位置 | 章节划分降低阅读负担，不会降低一个大变更的合并、发布或回滚风险 |
| 先理解整体设计与上下文 | 首屏提供意图、章节地图与关键入口，随后下钻到符号、diff 和完整文件 | 摘要应展示分析范围；未展开部分不能被默认为无风险 |
| 契约与不变量显式化 | 展示输入输出、错误语义、状态转换、资源所有权及其变化 | 不变量需要区分“作者要求”“代码观察”“AI 假设” |
| 测试验证行为 | 将行为变化关联到测试断言、边界场景与失败路径 | 测试文件存在、测试通过与充分覆盖是三件不同的事 |
| 反馈具体、说明原因、区分严重程度 | finding 包含问题、证据、影响与期待行为；区分 must-fix、question、nit | 风格偏好不应自动升级为阻断问题 |
| 自动化处理机械检查 | 将 lint、类型检查、静态分析结果作为证据输入，让人关注设计和行为 | 工具未运行、运行失败与检查通过必须分别显示 |
| 决策与版本可追溯 | 阅读记录、批注、证据与判断绑定到明确快照 | 代码更新后重新计算有效性，不能继承过期结论 |
| 发布后验证与可恢复性 | 长期支持记录灰度计划、监控信号、兼容性与回滚限制 | Review 通过不等于可以自动发布；迁移可能需要前向修复 |

Google 的评审指南强调检查设计、行为、复杂度、测试和上下文；本文据此设计检查维度，而不是让 UI 只突出 AI 找到的疑似 bug。[参考：What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。

Google 的小变更指南强调自包含、相关测试和整体可工作的提交。Unfold 的叙事章节允许中间提交无法编译，因此它们是**阅读视图**，不能被直接等同为可独立合并的 stacked PR。[参考：Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)。

批注应解释原因并标明必须修改还是建议；产品用结构化 finding 帮助保留这种语义。[参考：How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html)。

长期发布视角可借鉴 canary 的渐进暴露与监控验证思路；它属于部署验证层，不替代代码检查。[参考：Canarying Releases](https://sre.google/workbook/canarying-releases/)。

## 5. 产品体验

### 5.1 首屏：先建立整体认识

首屏包含任务来源、base 与 snapshot、变化规模、章节顺序、待处理 findings，以及分析能力状态。变化说明采用“旧行为 → 新行为”的表达，例如“上传调用返回时已完成 → 上传调用返回时仅完成入队”。

风险排序应给出理由，如跨线程、持久化格式改变、公共接口改变或错误路径删除。无法确认的依赖应标为未知。避免展示无依据的“安全分数”或“未受影响”断言。

v1 先用章节导语实现这一体验，不要求第一版就构建完整的行为图谱。

### 5.2 章节：一个理解目标，一组验证问题

以“纹理上传改为异步”为例，可组织为：

1. 上传接口：返回值、完成语义与失败通知是否改变？
2. 队列和 worker：调用如何跨越线程边界？
3. 生命周期：纹理是否存活到回调结束？
4. 关闭流程：队列排空、取消与回调顺序如何处理？
5. 测试：正常路径、失败路径、关闭时仍有任务的场景如何验证？

每章说明为什么现在看、与前章的关系，并提供代码锚点与完整原始 diff。依赖不确定时保留提示，允许人调整阅读顺序。

v1 planner 仅按整文件分配章节，无法保证一个跨文件行为正好对应一章。这是交互与聚类质量的待验证限制；数据接口保留 hunk 粒度，为后续符号级组织留出空间。

### 5.3 证据：解释必须可回到代码

一条重要解释应携带：结论、出处、代码证据、适用版本与未知项。点击证据进入真实编辑器，保留定义、引用和类型导航能力。

例如“纹理所有权延长至回调结束”需要引用对象捕获、队列保存与释放位置。只看到 lambda capture，只足以支持某个局部观察，不能推出所有关闭路径都安全。

原始任务表达期待行为；代码体现当前实现；测试提供特定场景的观察。三者相互校验，不能把 agent 的“我已完成”作为实现正确的证据。

### 5.4 反馈与增量重看

reviewer 在代码或解释上建立 finding，明确问题、影响和期待行为。批注锚定到终态快照，使 agent 能在原工作区定位。

下一轮展示相对于上一轮 snapshot 的增量，并将相关 finding 转为 needs-recheck。人确认后才 resolved；agent 声称修复或进入 idle 不构成解决证明。

文件未变时可保留 v1 的 reviewed@blob-hash 阅读记录。长期语义验证状态还应考虑依赖变化：调用方、契约或共享类型改变，即使本文件未变，也可能使先前判断失效。

## 6. 核心技术抽象：Review IR

Review IR 是变更、解释、证据与评审状态的结构化连接层。它应先支持现有章节闭环，再逐步增加语义分析，不在 v1 建设完整的全语言程序分析平台。

### 6.1 最小数据模型

| 实体 | 关键内容 | 作用 |
|---|---|---|
| ChangeSet | repo、base、snapshot、round、schemaVersion、分析范围 | 固定讨论对象与版本 |
| Chapter | 稳定 id、顺序、导语、file/hunk 分配 | 组织阅读路径 |
| Evidence | snapshot、路径、blob hash、范围、来源、工具信息 | 支撑解释与可靠跳转 |
| Claim | 内容、类型、evidenceIds、出处、已知限制 | 分离事实、意图与推测 |
| Finding | kind、origin、severity、anchor、status | 承载人和 AI 的反馈 |
| ReviewRecord | 版本、对象、阅读或验证动作、时间 | 保存评审进度 |

已有 plan、round 和 finding 模型继续作为 v1 主体。Claim 与独立 Evidence 实体是建议扩展，应通过 schemaVersion 与显式迁移引入，不直接改写已确认接口。

### 6.2 事实与推断分层

- **确定性事实**：文件修改、符号位置、hunk 分配、树是否相同、工具实际执行结果。
- **静态分析结果**：解析能力范围内的引用、调用候选和诊断；不完整分析必须保留限制。
- **AI 推断**：意图解释、语义聚类、风险假设；必须引用证据，不合格输出可拒绝或降级。
- **人类判断**：需求符合性、风险接受与批注解决；保存判断所针对的版本。

Schema 校验能保证结构，证据定位能保证引用存在，二者都不能保证解释语义正确。还需要冲突检测、抽样人工复核与评估集。

### 6.3 完整性账本

所有 diff hunk 必须进入一个明确的章节分配位置。语义单元可以互相引用同一证据，但底层 hunk 分配必须恰好一次，以便检测遗漏。

同时显示三种不同覆盖：**变化已归档、变化已解释、变化已被人检查**。二进制、生成文件、无法解析内容进入明确的未解释清单。覆盖账本证明的是已登记对象的完整性，不能证明所有运行行为都已发现。

## 7. 实现架构与可靠性

### 7.1 延续现有包边界

`packages/core` 管理 Git 快照、规划、确定性重放、校验、批注状态和 agent adapter；不依赖 VS Code。`packages/vscode` 承载章节 UI、真实编辑器导航、批注交互和终端投递实现。

核心数据在仓库外保存，叙事 worktree 停留在终态。AI 调用沿用本机 CLI adapter；命令与能力通过契约测试确认，本文不将交接中的具体 CLI flag 当作长期保证。

### 7.2 AI 负责解释，确定性程序负责代码操作

快照使用临时 index，不修改源工作区、真实 index、stash 或源分支历史。章节内容由既有 Git 对象和 diff 构造，AI 不生成中间代码。

最终必须验证 `tree(narrativeHead) == tree(snapshot)`。这证明两者 Git 树内容一致，不证明测试通过或行为正确。校验失败时停用叙事结果，保留终态快照的普通 diff 阅读。

AI planner 输出先过 schema，再校验真实引用、完整分配与跨轮稳定性；失败时有限重试，之后使用规则 planner。AI 不可用时仍能阅读、批注和导出。

### 7.3 快照与回合需要一致性边界

临时 index 解决“不干扰 agent”，但不能天然保证在 agent 持续写文件时取得应用层原子快照。建议在 agent 暂停写入时开始，检查采集前后的变化；若检测到并发修改，则提示重试，不能把混合时刻的内容当成可靠回合。

状态文件采用原子写入；每轮记录输入 SHA、plan、校验结果与执行阶段。refs 保持 snapshot 可达，进程中断后可恢复或清理未完成步骤。重复执行同一阶段应避免重复创建有效回合。

agent busy → idle 仅作为重新采集的触发候选。第二轮完成性由新快照、工具结果与人工重看确认。

### 7.4 输入边界与执行权限

仓库代码、注释、PR 文本与 agent trace 都属于待分析数据，不能作为工具执行指令。解释任务应尽可能只读，Git 修改由受约束的程序路径执行。

分析代码不应自动执行仓库中的构建脚本。测试执行采用单独动作，记录版本、环境与命令；既有 agent 测试输出若不能核实来源，只显示为作者提供的信息。

会话投递沿用已确认的目标选择与降级机制；多个候选时不能猜测。日志与可选导出避免携带凭据，明确哪些内容会交给模型提供方。本地 CLI 并不代表模型推理发生在本机。

### 7.5 解释的增量更新

缓存键至少包含 base/snapshot、输入证据 hash、分析器版本、模型与 prompt hash。新一轮按变化重新计算，并明确标记旧版本解释。

先实现现有文件级重看，再在有可靠符号依赖数据后扩展影响失效。动态调用、反射、宏和跨仓库依赖无法解析时保留 unknown，避免伪造完整调用图。

## 8. 分阶段交付与验收

| 阶段 | 交付重点 | 验收重点 |
|---|---|---|
| A：可靠阅读闭环 | 快照、整文件章节、字节一致重放、TS/Kotlin 导航、批注、投递、增量重看 | 源工作区不受干扰；所有 hunk 被分配；批注不静默丢失；AI 不可用仍可工作 |
| B：证据化理解 | Claim/Evidence、行为差异、契约问题、测试关联、未解释清单 | 重要解释可定位到当前版本证据；范围与未知项可见；人能纠正分组和解释 |
| C：更细粒度验证 | 符号/hunk 章节、依赖变化失效、状态/副作用分析、语义验证记录 | 分组质量提升；相关变化触发重看；误报与遗漏可测量 |
| D：团队与交付 | PR 输入、多人状态、导出导入、CI 与发布证据、可选跨仓库分析 | 明确权限、版本一致性、评审职责与数据边界 |

阶段 A 是现有 v1 路线；B–D 是本文建议。每阶段以用户价值和可靠性证据决定是否推进，不以接入模型或支持语言的数量作为完成标准。

## 9. 如何判断产品有效

### 9.1 北极星：建立可靠判断所需时间

采用交接文件提出的 **Time-to-Confidence（TTC）**，定义为从开始评审到 reviewer 能依据证据作出明确判断的时间。判断可以是接受、拒绝、要求修改或需要更多信息。

必须与理解正确率和遗漏风险一起观察。单独降低 TTC 可能只是让人更快相信错误解释。

### 9.2 第一轮实验

建议选取 12–20 个去标识化的真实变更作为探索样本，包含小修复、跨文件功能、重构和并发/错误路径变化。这是初步研究规模，不足以作行业统计结论。

对比原始 diff 与 Unfold；采用匹配任务并交错分配，避免同一人第二次阅读同一变更带来的记忆优势。由独立工程师根据代码、需求与可复现测试形成参考答案，不能用生成解释的同一个模型作为唯一裁判。

记录：

- 意图与行为问题的回答正确率，以及作出判断的 TTC。
- 已知问题漏检率、错误解释接受率与误报负担。
- 从结论定位到证据的时间、导航跳转与中断后恢复成本。
- 第二轮是否发现修复不完整或新引入的问题。
- 主观信心与实际正确率是否匹配。

合并后缺陷作为后续观察指标，需要控制变更复杂度和观察窗口，不能把简单的前后对比当作因果证明。

### 9.3 建议的初始产品门槛

以下是待验证的目标，不是当前测量结果：

- 在匹配任务上，TTC 中位数争取降低 25%，理解正确率不下降。
- 所有展示的重要 AI 结论都带可解析引用或显式标为证据不足；另行测量引用是否真正支持结论。
- diff hunk 归档覆盖率 100%，无法解释部分明确展示。
- 当前版本与过期证据不得混用；锚点失效与重新定位歧义不得静默处理。
- 核心 Git 不变量通过真实仓库测试；AI 故障不阻断基础阅读闭环。

## 10. 开发过程也应遵循这些原则

实现按可独立验证的纵向切片推进。Git 安全操作、状态迁移、锚点与 adapter 等关键能力先写有价值的失败用例；UI 文案与可逆布局修改通过实际阅读体验检查。

测试重点是产品承诺：快照不动源状态、重放终态一致、新增/删除/重命名可处理、快照 ref 经 GC 仍可达、批注不漂移、回合中断可恢复。符号解析扩展后补充语言 fixture；真实 CLI 契约测试与常规离线测试分开。

AI 质量单独建立固定评估集，覆盖错误引用、无支持结论、漏归档、跨轮解释过期与恶意注释。保存模型、prompt、输入版本和原始输出，使退化可定位。

关键权衡写入简短 ADR：为什么终态字节一致、为什么中间章不要求编译、为什么 core 独立于 UI、为什么回合状态在仓库外。记录理由与可推翻条件，避免愿景草案中的远期需求变成提前抽象的负担。

## 11. 下一步需要验证的产品问题

1. 用户最需要的章节顺序是契约优先、测试优先，还是入口路径优先？允许按变更类型调整。
2. 整文件分章在哪些真实变更上已经足够，在哪些场景必须进入符号级？
3. 什么证据能有效帮助人校验解释，又不会增加额外阅读负担？
4. 如何让语义检查记录有价值，同时避免把勾选变成合规仪式？
5. 跨轮保持章节稳定与重新组织阅读顺序发生冲突时，用户更看重哪一项？

建议先完成阶段 A，拿第一用户的真实工作流验证“按章阅读与增量重看”能否减轻负担，再决定阶段 B 的 Claim/Evidence 模型与交互细节。
