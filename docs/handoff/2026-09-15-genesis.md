## 0. 一句话

**Unfold**：一个专注 "code review + AI" 的 VS Code 插件（可能加 CLI 内核）。
核心主张：agent 一天能产几万行代码，没人做"把做出来的代码整理成人类能读的样子"。
Unfold 把一段改动**重新讲一遍**——切新 worktree、按循序渐进的阅读顺序重提交、保证提交树字节一致——再把跳转 / 批注 / 重看 / 批注发回 agent 做到极致。

Tagline（用户已写进 README）："Unfold your change before you review it"。中文语境叫「展开」，内部昵称「章回」。

## 1. 用户与合作方式（本项目特有的部分）

- 用户是 deepshape 的技术负责人，重度 orca 用户（多 worktree、多 agent 并行；Claude Code + Codex；`/review-loop` 让 claude/codex 互审、`/cpd` 一键发布）。这个插件是他自己每天要用的东西，**第一个用户就是他**。

- 流程走 superpowers 的 brainstorming（architectural path），**一次只问一个问题**，每个设计小节都要他点头。

## 3. 未定的决策（接下来该问的问题，按顺序）

1. **架构第一刀：CLI 内核 + VS Code 插件，还是纯插件？**
   我的推荐是拆：内核 `unfold narrate <range>` 吃一个 git range，产出叙事分支 + 叙事文件 + 校验；插件只做阅读、批注、重看、导出。理由：内核能被 orca hook / CI / `/review-loop` 直接调用，叙事分支不开编辑器就能推成 PR；两者互不绑死。代价：两个发布物 + 一个要维护的接口契约。纯插件上手快，但 git 手术和 AI 调用困在扩展宿主里，orca 那边永远用不上。**这个问题已经抛给用户，他没答（转去起名、建仓了），交接后先把它问回来。**
2. v1 的评审对象：用户工作流几乎肯定是 **A. 审 orca 各 worktree 里 agent 的本地改动、把意见喂回 agent 再来一轮**（而非 GitHub PR 或历史 commit 范围）。我猜是 A，**未经他确认**。
3. spec 落点：本仓没有 deepshape-stack 那种 `wiki/prd/` 覆盖，按 superpowers 默认写 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`。
4. 之后按 brainstorming：2–3 个 approaches → 分节设计逐节确认 → 写 spec → self-review → 用户 review → `writing-plans`。

## 4. 为什么它该存在（证据链，别再重新论证）

### 4.1 用户的原始痛点
1. 在 orca（ADE）里审代码，没有基于语法树的跳转；审代码不需要补全，只需要跳转。
2. ADE 刻意淡化 review：没有 JetBrains 的 bookmark、没有强 git。
3. 实测 VS Code Agents window 之后又加了三条：review 面板在侧栏、不能全屏、不是核心焦点；diff 面板不支持跳转；批注弱、不结构化。

### 4.2 市场四阵营（2026-09 查证）

| 阵营 | 代表 | 强 | 弱 |
|---|---|---|---|
| 平台 web review | GitHub / GitLab PR、Gerrit、Graphite、Reviewable、Google Critique | 评审**状态**：看到哪个版本、push 后只看增量、attention set、评论跟着行走 | 没导航（Sourcegraph 当年用浏览器插件往 GitHub 页面塞跳转就是补这个洞） |
| IDE 内 review | GitHub PR 扩展、JetBrains 内置、GitLens、CodeStream（已死） | 导航、上下文、bookmark | 只认 PR 不认本地 diff；没有"看过 / 改过没"的状态（GitHub Viewed 是最弱形态：文件一变整个重置，不给增量） |
| AI reviewer | CodeRabbit（IDE 版能审未提交改动、一键把评论打包给 agent）、Copilot review、Greptile、BugBot、Codex / Claude Code `/code-review` | 产"发现" | 产出是一坨评论不是**工作台**：人没地方 confirm / dismiss / 追问，也不能和自己的发现放一个列表 |
| ADE / 平台自带 review | orca（AI diff annotation）、Cursor、Claude Code desktop、Conductor、**VS Code Agents window** | 贴着 agent 循环 | webview diff、逐 hunk accept/reject、无 LSP、无跨轮状态、绑自家 session |

**空白 = 导航 + 评审状态 + 本地优先 + agent 中立，四者同时拥有的没有一家。**

### 4.3 关于"微软会不会把它做掉"的结论
- 我原先的反对意见（"平台会补齐"）被证据修正：VS Code 已经不是 Copilot 专属——1.137 的 agent harness 有 Copilot / Claude / Codex 四种，Claude 可用 Anthropic API key 或 `CLAUDE_CODE_OAUTH_TOKEN`（Anthropic 计费），Codex 免费 ChatGPT 账号即可。微软 2026-02 博客标题就是 *Your Home for Multi-Agent Development*——它要的是**面**（VS Code）和**枢纽**（GitHub Agent HQ），agent 是谁的可以让步。
- 但它的 review **与 session 绑死**：Changes 面板 / Add Feedback / Mark as Reviewed 只作用于 VS Code 自己 host 的 session。orca 终端里的 Claude Code、tmux 里的 Codex、CI 产的分支、同事的 PR、`/review-loop` 的产物，它一概看不见、评不了、反馈无处去。这是它的护城河，它没有理由解耦。
- **所以 Unfold 的必要性 = "一个与 agent 宿主解耦的 review 面"**：审任意 git range，不管谁在哪产出；反馈导出给任意 agent。微软结构上不会做，orca 技术上做不了（Electron + webview，不会去造 LSP）。
- 市场也没人做"把改动重新讲一遍"：PR Lens 有篇指南标题就叫 *Agent pull requests lose the narrative*，Salesforce 工程团队抱怨 agent PR "backend、config、tests、UI 一次全来"；LinearB 2026 数据 AI 辅助 PR 的 P75 是 408 行 vs 人写 157 行。所有人的答案都是"让 PR 变小"，没人做"让大 PR 可读"。

### 4.4 spike 结论（VS Code 1.137.0 Agents window，实测）
- **能用**：Claude 走用户自己的 OAuth token，Windows 本地 host 与 WSL 远程 host 都跑通；日志 `[Claude] Native account check: setUp=true, tokenSource=CLAUDE_CODE_OAUTH_TOKEN`，模型 5 个。
- **但 review 弱**（§4.1 第 3 条）。这就是产品成立的一手证据。
- **BYOK 的隐藏门槛链本身就是论据**（"存在于源码里，但对普通用户等于不存在"）：① `chat.agentHost.allowSignedOutWhenUsable` 实验开关（默认 false）；② token 必须在 Agent Host **进程**环境里（Windows 本地 host 读 Windows 用户环境变量，WSL host 读 WSL 侧 `~/.claude/settings.json` 的 `env`）；③ Claude Agent SDK **不随 VS Code 打包**，要从 `main.vscode-cdn.net/agent-sdk/claude/<ver>/<target>.tgz` 另下几百 MB，且下载按钮在 Claude session 里——Copilot Free 用户登录状态下 Claude 永远灰（`UpgradeRequired`），只能登出后进去下；④ WSL host 是另一个独立进程，SDK 要再下一次（我手动放到 `~/.vscode-server/data/agent-host/sdk-cache/claude/0.3.258/linux-x64/` + 空 `.complete` 哨兵，重启 host 才认）。
- 相关源码坐标（microsoft/vscode，tag 1.137.0）：`src/vs/platform/agentHost/node/claude/claudeTransportMode.ts`（"deliberately no host-global setting to prefer a transport"，7 月 PR #323037 的 `claudeUseCopilotProxy` 已删）、`.../claudeAgent.ts`（`_refreshModels` / `_fetchNativeModels`）、`.../agentSdkDownloader.ts`（cache 布局）、`src/vs/workbench/contrib/chat/browser/agentSessions/sessionTypeAvailability.ts`（Upgrade 门）、`src/vs/sessions/browser/sessionsAuthGate.ts`（窗口门）、`src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts`（"Connect to Remote Agent Host via WSL"）。
- 三个原本要 spike 回答的问题（`/` 里有没有他的 skills、hooks 触发不触发、多轮 Add Feedback + Mark as Reviewed 够不够用）**用户没有逐条报告**，他直接给出了"review 很弱"的总体判断并转向产品定义。不必再回头补。

## 5. 与用户对齐过的设计原则（spec 的骨架）

### 5.1 叙事分支（想法 1）——支点是"字节一致"
- 每个 review 任务切**新 worktree**，对要 review 的 range **重提交**成循序渐进的章节，**终态 tree 与原分支 tip 字节一致**。校验：`git rev-parse <orig>^{tree}` == `git rev-parse <review-tip>^{tree}`，不等就拒绝出货。
- 字节一致的真正价值不是安全，是**批注可移植**：任何锚定在终态（文件 + 行 + 内容 hash）的批注可 1:1 落回原分支。叙事分支因此是**可丢弃的视图**，永远不是第二份真值。
- **粒度 v1 = 文件级**：每个文件分到一章，中间 tree = "每个文件要么 base 版要么终态版"，构造确定性、无需 AI 生成中间内容；最后一章"其余"保证一致性。**hunk 级拆分是 v2**（一个文件横跨两章时才需要，是 tangled-changes 老难题、AI 出错处）；失败可检测（patch 不 apply / tree 不等）→ 退回文件级。
- 中间提交**不必能编译**；"每章能否单独 typecheck"是便宜信号，晚点加。
- 叙事 ≠ 只有顺序：每章要有"为什么先看这个"的一段话 + 指路锚点。**数据格式借 CodeTour**（微软，step = file/line + markdown，可绑 git ref，`.tours/*.json`），不自己发明，还能互操作。
- **章节分配要确定性、跨再生稳定**：agent 又推了 commit，只读"自上次 reviewed 之后的增量"（reviewed@hash 模型），批注 / 书签不能在章之间漂移。
- 顺序：默认 契约（schema / 类型 / 接口）→ 核心逻辑 → 接线与调用方 → 测试与文档；**AI 提议、人拖动、人的调整要存下来**（最有价值的信号）。
- 叙事分支**可以直接作为 PR 推上去**：tree 一致、merge 结果一样，GitHub 上逐 commit 看的人也拿到叙事——价值不锁在插件里。

### 5.2 吸纳各家最好的（想法 2）

| 能力 | 谁做得最好 | Unfold 怎么做 |
|---|---|---|
| 跳转 | VS Code 自己（diff 右侧是真文件） | 叙事分支在**自有 worktree**，右侧 LSP 全有；左侧（上一章状态）用**第二个 worktree**检出 → 两侧都能跳（web review 做不到；**待实测**，代价是 LS 索引两棵树） |
| 批注模型 | Critique / Reviewable：线程 + 解决状态 + 跨修订持久 | finding = kind（question / must-fix / nit / praise / bookmark）+ severity + status + 锚点（file, range, content hash）+ origin（human \| ai）。JetBrains 书签只是 kind 之一，不单做 |
| 重看 | Reviewable 的"文件 × 修订"矩阵 | 每条批注在下一轮显示"针对它的改动"，人只判"修没修对"；文件级 reviewed@blob-hash，改了变 stale、只展示增量 |
| 发给 agent | CodeRabbit 的"一键把所有评论打包给 agent" | 结构化 + 厂商中立：一个 findings 文件（JSON）+ 一段 prompt，Claude Code / Codex / orca 谁都能吃；另两个出口：GitHub review（API）、纯 markdown |
| 引导阅读 | CodeTour | 章节 = tour，step = 锚点 |

### 5.3 AI 只做两件事
生成阅读顺序（可点击的 checklist / tour）+ 产 findings 进同一个列表让人 triage。**不做** accept/reject，**不做**修复。

### 5.4 明确不做
git log/graph（GitLens + 内置 Source Control Graph 够了）、补全、forge 深度集成（v1 只 export）；**不用 webview 做 diff**（真实编辑器 + decorations，这是导航免费的前提）。

## 6. 风险（用户已知悉）
- 微软 Agents window 和 orca 都在往 "review agent diff + 回反馈" 砸资源，"更好看的 diff + 评论" 会被平台碾平；能活的只有它们结构上不会做的部分：agent 中立、跨轮状态模型、不绑 forge、叙事重提交。
- 单人维护 VS Code 扩展的长期成本（API 变动、diff editor 内部不稳定）→ **v1 必须窄到一个用户每天都会用的闭环**。
